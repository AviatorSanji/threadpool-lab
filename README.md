# Java 线程池与上下文学习笔记

## 1. 任务、线程与 Callable

- 任务描述要执行的工作，线程负责执行任务。创建任务对象不会自动执行它。
- `Callable<T>` 的 `call()` 可以返回类型为 `T` 的结果，也可以抛异常。`Callable<Void>` 通常返回 `null`。
- 可以通过 `implements Callable<T>` 的类定义任务，也可以通过 lambda 定义。
- 直接调用 `task.call()` 是普通方法调用，在调用它的线程中执行，不会自动创建或切换线程。
- 一个工作线程可以依次执行多个任务，任务与线程不是一一对应。

```java
Callable<Integer> task = () -> 10000 - 1000;
```

lambda 创建时定义工作；调用它的 `call()` 时才计算价格。

## 2. submit、Future 与 get

- `submit(task)` 提交任务，返回代表这个任务的 `Future<T>`，不是直接返回业务结果。
- 工作线程可能在 `submit()` 返回之前已经开始执行任务。
- 普通提交不会等待任务完成；采用 `CallerRunsPolicy` 时，任务可能在提交线程同步执行，使提交本身耗时。
- `future.get()` 取得任务结果。尚未完成时，等待的是调用 `get()` 的线程，其他工作线程可以继续执行。
- `get()` 不负责启动任务，也不会关闭线程池。
- 先提交全部任务，再逐个 `get()`，可以让多个任务重叠执行。每提交一个就立刻 `get()`，会推迟后续任务的提交。
- 结果打印顺序受调用 `get()` 的顺序影响，不一定与任务完成顺序相同。
- 成功取得结果后，调用线程能够看到该任务执行期间的写入。因此可以等待任务完成后再读取它的日志。

| 任务状态 | `Future.get()` 的表现 |
| --- | --- |
| 正常完成 | 返回业务结果 |
| 执行失败 | 抛出 `ExecutionException`，`getCause()` 可取得原始异常 |
| 已取消 | 抛出 `CancellationException` |

任务执行失败与任务提交被拒绝是不同阶段的错误。

## 3. invokeAll 与批次执行

- `invokeAll(tasks)` 提交一批任务，等待所有任务完成后返回，包括异常结束的任务。
- 返回的 `Future` 列表与输入任务列表顺序一致，不按实际完成顺序排列。
- 它不保证任务的开始或完成顺序，也不负责合并业务日志。
- 单个任务执行失败，会记录在对应的 `Future` 中；不会因此自动快速结束整个批次。
- 提交过程中被拒绝时，JDK 的 `invokeAll` 会取消本批次尚未完成的 Future，再把拒绝异常向外抛出。这不等于中断整个线程池的所有任务，也不会撤销已产生的业务修改。

```text
输入任务：    [A, B, C]
实际完成：    B、C、A
返回列表：    [Future A, Future B, Future C]
按列表合并：  A、B、C
```

`invokeAll(tasks, timeout, unit)` 使用整批任务的等待预算，包含排队和执行时间。预算耗尽后取消未完成任务，通过返回的 Future 表示取消；它不会仅因预算耗尽直接抛出 `TimeoutException`。

等待预算不是强制停止期限。同步执行任务的拒绝策略、任务对中断的响应、线程池关闭时的等待，都可能使调用或整个程序耗时超过预算。

## 4. 取消与中断

- Future 进入取消状态，不代表任务代码已经退出，任务的 `finally` 可能仍在运行。
- `cancel(true)` 会尝试中断正在执行任务的线程；中断是一种通知，不是强制杀死线程。
- `Thread.sleep()`、`CountDownLatch.await()` 能响应中断，抛出 `InterruptedException`，并清除中断标志。
- 捕获中断后只打印、不继续抛出，后面的业务代码可能继续执行。需要结束当前任务时，可以继续 `throw e`。
- 即使任务忽略中断、后来返回结果，已取消的 Future 也不会恢复成成功状态。
- “主线程确认取消”和“工作线程打印中断”发生在不同线程，打印顺序不固定。
- `isDone()` 包括正常完成、失败和取消，不能用它证明被取消任务的执行代码已经停止。

## 5. ThreadPoolExecutor 的线程与队列

| 参数 | 含义 |
| --- | --- |
| `corePoolSize` | 工作线程数量未达到这个值时，提交任务优先创建线程 |
| `maximumPoolSize` | 工作线程数量的上限，不代表立即创建这么多线程 |
| `workQueue` | 保存等待执行的任务 |
| `keepAliveTime` | 默认情况下，超过核心数量的线程空闲多久后可回收 |

接收任务的主要顺序：

1. 工作线程数量不足核心线程数：创建线程执行任务。
2. 已达到核心线程数：尝试把任务放入队列。
3. 队列无法接收：尝试增加线程，直到最大线程数。
4. 线程和队列都无法接收：执行拒绝策略。

- `newFixedThreadPool(n)` 将核心和最大线程数都设为 `n`，使用未指定容量的 `LinkedBlockingQueue`。
- 未指定容量的 `LinkedBlockingQueue` 通常称为无界队列，实际上仍有容量上限，并非无限内存。
- 只要队列还能接收，线程池通常不会扩展到核心线程数以上。因此，单独提高最大线程数未必增加并发执行数。
- `ArrayBlockingQueue<>(1)` 的容量为 1，只能容纳一个等待任务；正在执行的任务不占队列位置。
- 队列满后，新任务可以直接交给新建线程，因而比之前排队的任务更早开始。队列的先进先出不等于所有任务按提交顺序开始。
- 用 `sleep` 模拟耗时便于观察调度，不能据此推断真实算价性能，也不能保证固定打印顺序。

## 6. 拒绝策略与线程池生命周期

| 策略 | 池仍在运行但无法接收任务时的行为 |
| --- | --- |
| `AbortPolicy` | 向提交方抛出 `RejectedExecutionException`，不主动取消其他任务 |
| `CallerRunsPolicy` | 由提交任务的线程执行当前任务，增加提交方耗时 |

- `AbortPolicy` 本身只拒绝当前提交。批次中的其他任务被取消，是 `invokeAll` 的收尾行为。
- 逐个提交异步日志、捕获拒绝并返回失败状态，不会自动取消已有日志任务。
- 日志池使用 `CallerRunsPolicy` 时，过载日志可能回到请求线程执行，把编码、压缩等耗时加到请求处理中。
- 默认线程工厂创建非守护线程。`main()` 结束后，线程池工作线程仍存活，JVM 可能继续运行。
- `shutdown()` 停止接收新任务，允许已提交任务继续执行，但调用本身不等待线程池终止。
- JDK 21 的 `ExecutorService` 支持 `try-with-resources`。退出代码块时调用 `close()`，发起关闭并等待线程池终止，异常路径也会执行。
- `close()` 的等待不是固定超时；任务不退出时，关闭可能继续等待。
- 生命周期由创建和管理线程池的一方负责。短期演示的池用完关闭；服务中的共享池通常跨请求使用，在应用关闭时统一清理。

## 7. ThreadLocal 的存储与访问

- 普通 `ThreadLocal` 的默认初始值为 `null`。
- 每个 `Thread` 对象拥有自己的 `threadLocals` 存储表。键是 `ThreadLocal` 对象，值是用户保存的对象引用。
- `get/set/remove` 先通过 `Thread.currentThread()` 找到执行线程，再操作该线程自己的表。
- 同一个 `ThreadLocal` 对象可以被多个线程访问，但各线程查询的是各自的记录。
- `set(value)` 设置当前线程的值；`remove()` 只移除当前线程的对应记录。
- `remove()` 后再次 `get()` 会重新使用初始值；不会去主线程查找值。
- 主线程的设置不会自动传递给池里的工作线程。传递同一个 ThreadLocal 对象引用，也不等于传递主线程表里的值。
- lambda 可以捕获 ThreadLocal 对象引用；普通任务类可以通过构造方法接收引用并保存到字段中，不要求使用 `static`。
- 线程池会复用工作线程。不清理时，后续任务可能读到前一个任务留下的值。

## 8. 绑定隔离与对象共享

ThreadLocal 隔离的是线程里的绑定记录，不负责复制值对象。

```text
主线程记录：   context → parent 对象
工作线程记录： context → 同一个 parent 对象
```

这时只有一个上下文对象，没有两个对象副本。工作线程修改它的日志列表，主线程之后读取的是同一个列表。

- `remove()` 移除绑定，不会清空该对象的字段，也不会删除其他线程的绑定。
- 想让日志独立，需要为任务创建新上下文、新日志列表。
- 本例 `forWorker()` 用相同请求 ID 构造新上下文；不可变字符串可以共享，日志列表每次新建为空。
- `final List` 固定的是列表引用，不代表列表内容不可修改。
- ThreadLocal 不自动保证共享对象的并发安全。

## 9. 上下文捕获、绑定与恢复

| 值 | 读取时机 | 用途 |
| --- | --- | --- |
| 捕获的父上下文 | 调用包装方法时 | 确定任务应该使用的上下文 |
| 执行线程的旧上下文 | 包装任务真正执行时、绑定之前 | 确定结束后应恢复什么 |

任务执行过程：保存执行线程旧值 → 绑定任务上下文 → 执行业务 → 在 `finally` 中恢复旧值。

- 原来没有上下文：结束时移除任务的绑定。
- 原来有上下文：结束时恢复原值，避免破坏外层调用。
- 恢复适用于 `CallerRunsPolicy`、直接调用包装任务、嵌套任务等已有上下文的执行场景，不只适用于某一种拒绝策略。
- 捕获与保存旧值发生在不同时间，可能得到不同值，不能混用。
- 恢复或清理必须在实际执行任务的线程中完成，主线程的清理不能代替工作线程的清理。

## 10. 任务包装与 return / finally

- 包装方法返回一个新的 Callable；调用包装方法时只创建任务，不会立即执行返回的 lambda。
- 包装任务执行时，先处理上下文，再通过 `task.call()` 调用原业务任务。这个普通调用继续使用同一个执行线程。
- 包装方法的 `return lambda` 返回任务对象；lambda 内部的 `return task.call()` 返回业务结果，两者不是同一个返回动作。
- 正常返回时，先计算 return 表达式，再执行 finally，最后返回之前取得的值。
- 清理 ThreadLocal 不会清除已经取得的返回值。因此可先看到工作线程的清理输出，再看到主线程打印结果。
- finally 若抛异常，会影响任务的最终结果；不能把“进入 finally”理解为任务已成功完成。

职责可以分为：业务任务执行计算；包装层管理上下文和日志移交；执行层提交任务并等待；收集器保存任务日志。

## 11. 日志隔离、收集与合并顺序

- 每个任务只写自己的日志列表；主线程等待正常完成后再读取、合并，可以避免多个任务同时修改父日志列表。
- `addAll()` 添加日志条目，不会让两个列表变成同一个对象。本例日志条目是不可变字符串。
- 当任务返回上下文时，可按 invokeAll 返回的 Future 列表顺序读取和合并。
- 当任务返回价格或 Void 时，日志需要独立传递给收集器；业务返回值与日志收集不必绑定。
- 收集器为每个任务预留位置，按任务下标使用 `set(index, logs)`，而不是按完成顺序追加。
- 日志顺序由固定下标和按下标读取共同保证，invokeAll 不会重新排序一个另外维护的收集器。
- 收集日志列表的副本、返回独立快照，可以避免外部修改内部列表。本例复制的是列表结构，不是深拷贝所有条目对象。

## 12. synchronized、closed 与超时收尾

- synchronized 实例方法锁住当前对象 `this`。多个任务共享同一个收集器，才会使用同一把锁。
- 使用同一把锁协调收集、读取和关闭操作；锁只保护这些操作，不必覆盖整个业务计算。
- 对 closed 的检查与实际写入要在同一个临界区内；单独保护某一个步骤无法完整协调收尾。
- 关闭操作在同一把锁下完成：设置 closed → 生成日志快照 → 清空内部列表。
- 日志合并可以在取出快照、释放锁后，由主线程完成。
- 工作线程收集前检查 closed，关闭后不再写入，避免重新持有日志，也避免向已清空的列表 set 时越界。
- 日志是否进入最终快照，取决于收集和关闭谁先完成；关闭后的迟到日志不会进入快照。
- 主线程在 finally 中收尾，适用于正常结束、超时、异常和提交失败等路径。
- 关闭收集器不等于终止线程池，也不等于工作任务代码已退出。

## 13. CountDownLatch 与执行顺序控制

- `new CountDownLatch(1)` 创建初始计数为 1 的门闩。
- `await()` 在计数非零时等待；可因中断抛出 InterruptedException。
- `countDown()` 减少计数；达到零后放行等待者，后续 await 也可以直接继续。
- 门闩可以控制“先收尾、后提交迟到日志”等顺序，避免用 sleep 猜测另一个线程是否已执行。
- 取消 Future 不等于把门闩计数减到零。任务响应中断进入 finally 后，仍可能继续等待别的条件。
- 演示中必须先放行等待任务，再退出线程池资源块，否则 close 等待任务退出，而任务又等待主线程放行，可能互相等待。
